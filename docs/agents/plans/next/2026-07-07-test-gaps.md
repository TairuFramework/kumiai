## ~~High — worth its own branch~~ CLOSED 2026-07-28

**The app-lane drain's retention guard survived deletion with the whole rpc suite green** —
`app-lane.ts:464`, `if (retentionOf(protocols[name], prc) !== 'log') continue`. The guard is the
only thing standing between a hostile member and *"make every returning member re-fire an ephemeral
handler out of the log"*.

**The cause was not a missing test.** `peer-app-drain-integrity.test.ts:352`, *"a retained frame
naming an ephemeral procedure is not delivered"*, already forged exactly the right publish. It was
neutralised one layer down, in the fixture:

`createFakeCrypto` models a real handle's consumed message key with a `spent` set keyed
`epoch:senderDID:generation`, and every instance starts at generation 0. The test dispatched a real
`chat/posted` from alice's peer (spending `1:alice:0` on the reader) and then forged the ephemeral
frame from a **fresh** `createFakeCrypto({ epoch: 1, localDID: 'alice' })` — also generation 0. The
forged frame was refused by `unwrap` as a spent key and died at `app-lane.ts:435`, forty lines above
the guard under test. `expect(changed).toEqual([])` passed because nothing was ever opened.

Fix: burn a generation on the forging instance before the forge, with a comment saying why. The
test now fails on the mutation — `expected [ { text: 'alice is typing' } ] to deeply equal []` —
and 374/374 pass restored.

**The general shape.** A negative assertion behind a forged frame is only as good as the forge. The
other two in `packages/rpc/test` were checked and are sound: `directed.test.ts:221` forges as
`mallory`, a DID no peer ever sends as, so its generation 0 is fresh;
`peer-anchor-advance.test.ts:194` asserts *delivery*, so a collision would fail it loudly. The
commit-lane forgers use the ledger seal, which has no `spent` set at all.

- Peer/handle concurrency, the `encrypt`/`processMessage` half — **void; the plan's premise was

  2026-07-12, commit `b7a3545`) already covers this: `:3011` gives concurrent encrypts on one

  that "`mutex.test.ts` covers the mutex in isolation, not the handle" traced back to the 2026-07-02
  audit and was never re-checked against `group.test.ts`; it was false as of 2026-07-12. No test
  written 2026-07-31 — none was needed.
- Peer/handle concurrency, the `dispose()` half — closed by `rpc/test/peer-dispose-race.test.ts`,
  mutation-verified for `to()` and for `resync()`, plus a shipped source fix. The probe found a
  real defect, not the one originally predicted: `to()` handed back a `Client` over an
  already-aborted transport, and the mirror ordering (teardown first) reported a misleading
  `Unknown protocol` for a peer that no longer exists — both mutation-verified 2026-07-31. A
  post-dispose `resync()` also rebuilds the epoch's clients and re-populates the mux's
  `listeners`/`refcount` — a real, mutation-verified local leak — but nothing reaches the hub:
  `mux.dispose()` deliberately leaves `subscriptions` standing, so `retain` finds every topic
  already held and never re-subscribes (`peer.ts:2025-2029`). An earlier review round guessed a
  different mechanism, that dispose left topics free for `resync()` to re-register into hub calls
  nothing would release; that guess was wrong and is not what shipped. `commit()`, `replay()`, and
  `recover()` are guarded the same way and the changeset asserts `commit()` would otherwise publish
  to the hub from a gone peer, but that specific claim has no biting test of its own — mutation
  coverage of the extension is `resync`-only. Fixed in `packages/rpc/src/peer.ts` with a `disposed`
  flag and an `assertLive()` guard checked immediately after `await ready` at every entry point
  (`commit`, `replay`, `recover`, `resync`, `.to`, `.dispatch`/`.request`/`.gather`) — see
  `.changeset/peer-disposed-guard.md` (`@kumiai/rpc` minor).
  `backlog/2026-07-07-rpc-peer-lifecycle-hardening.md`'s "Test hooks" section is updated to match.
- Encrypt from a restored handle after an epoch change (the reseal half) — **settled as
  not-isolable; no test written.** The sibling test, `tests/integration/test/app-lane-delivery.test.ts:604`,
  proves bob's post-walk epoch-3 secrets match alice's, via successful decrypt. It does **not**
  exercise the outbound path (wrap → wire → alice's handler) at all. That path is genuinely
  untested — but no mutation reachable from this test's shape (a restarted member only *receiving*
  catch-up commits) can separate "decrypt right, seal wrong," because `processCommit`
  (`mls-rpc/src/mls.ts:146-171`) applies received commits by mutating the handle **in place** and
  never calls `adopt()`; restore → walk → reseal all share one single mutable object with no
  reference to freeze. This is neither "already covered" nor "closed" — it is a real gap this
  entry's shape cannot reach. A restarted member that *authors* a commit reaches `adopt()` and can
  isolate the same risk; that distinct entry is filed separately at
  `backlog/2026-07-31-mls-rpc-author-path-stale-handle-reseal.md`.
